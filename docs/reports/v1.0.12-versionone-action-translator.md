## Report Version
v1.0.12

## Purpose
Execute the v1.0.11 highest-leverage move: replace the misrouted `structuralizeAfter` call on the First Buildable Version section with a dedicated `synthesizeVersionOne` that produces concrete form/scope/proof statements rather than generic after-state fallback. Close the v1.0.9 gap where 9 of 10 personas received the same fallback paragraph for the most concrete blueprint section.

## Trigger
User prompt **"VisionAir VersionOne Action-Translator Pass"** on 2026-04-21, executing the singular next move identified in v1.0.11 under the Highest-Leverage Move Contract.

## State Observed (pre-execution)
`app/session/page.tsx` constructed `blueprintData.versionOne` by routing the user's version-one description through `structuralizeAfter`:

```ts
versionOne: state.versionOne.trim()
  ? structuralizeAfter(state.versionOne).join(' ')
  : '',
```

`structuralizeAfter` is calibrated for emotional/state words ("clear", "confident", "free", "structured", "capable", "seen"). Action+scope descriptions like *"A CLI that ingests a single trace file… No backend, no UI, no integrations"* (P1) or *"A Notion template + 30-day onboarding email course"* (P10) trigger zero matches → fallback bullets fire → the most concrete blueprint section becomes the most generic.

v1.0.9 confirmed this empirically: only P10 had any after-state matches; the other 9 personas received the same generic *"The new state introduces a defined structural shift…"* paragraph regardless of the actual product/scope they described.

## Action Taken
Modified only `app/session/page.tsx`. No other file touched. Two sequential edits:

### Edit 1 — Add `synthesizeVersionOne` helper inline
Added below the v1.0.11 capability synthesizer, before `formatProblemSpace`. Consists of:

- **`versionOneFormPatterns`** — 35 form-noun regexes ordered with multi-word forms first (`web app`, `email course`, `Notion template`, `landing page`, `brand sprint`, etc.) so they win over single-word fallbacks (`tool`, `app`)
- **`versionOneActionVerbs`** — 27 action-verb regexes covering builder vocabulary (ingests, drafts, classifies, renders, generates, automates, sorts, surfaces) plus instructional vocabulary (guides, teaches, walks through, defines)
- **`verbsThatTakeDirectObject`** — small set of verbs that should be followed by the target directly without "for" (helps founders, not "helps for founders")
- **`detectVersionOneForm`** — first-match wins (multi-word ordering ensures specificity)
- **`detectVersionOneAction`** — earliest-by-text-position match wins (so the user's first/primary verb leads the sentence)
- **`detectVersionOneScope`** — multi-strategy detector:
  1. Exclusion phrases ("no backend, no UI, no integrations") collected via global regex; up to 3 listed
  2. Duration windows ("4-week", "30-day", "6-week")
  3. Participant caps ("cap at 8")
  4. Fixed scope/price language
  5. Static scope phrases ("smallest meaningful", "minimum viable", "v1", "only/just", "bounded/limited", "lightweight")
- **`composeVersionOneFormBullet`** — produces *"Version one is a [form] that [action] for [target]."* (or direct-object variant) when all three are present; gracefully degrades to *"Version one is a [form]."* when target/action absent; final fallback *"Version one is a build whose form has not yet been explicitly named."*
- **`composeVersionOneScopeBullet`** — switches template based on scope shape: *"Scope is intentionally bounded by what is excluded: [exclusions]"* for exclusion lists; *"Scope is intentionally bounded to [phrase]"* for everything else; explicit non-fallback phrasing when no scope detected
- **`composeVersionOneProofBullet`** — pattern-matches the input for proof-style language: `validate` → "whether the value is real enough to validate"; `pay`/`charge`/`$N` → "whether real users will actually pay"; `see if`/`test if` → "whether the smallest version of the offer matches what users actually need"; default → "the core transformation can happen in a real, testable form"
- **`synthesizeVersionOne`** — empty input → fallback; no form AND no scope detected → fallback (preserves "fallback when nothing recognizable" semantics); otherwise composes 3 bullets

Reuses `detectCapabilityTargets` from the v1.0.11 capability block for target detection (engineers, founders, students, women, etc.) — same target vocabulary, no duplication.

### Edit 2 — Rewire blueprint versionOne source

-    versionOne: state.versionOne.trim()

+    versionOne: synthesizeVersionOne(state.versionOne).join(' '),

`structuralizeAfter` is still used by `formatTransformation` (the transformation surface) — only the versionOne wiring changed.

### Why This Move

- **Impact relative to alternatives**: idealUser is now the highest-fallback blueprint section (40% fallback rate, vs ~20% for versionOne post-v1.0.12 and ~0% for capability post-v1.0.11). Fixing it would lift Structural Cohesion and User-Intent Fit across ~4 personas without touching the ones already working.
- **What it unlocks**: Capability + Ideal User + Transformation + VersionOne form a coherent narrative chain — *who the user is → what blocks them → what changes → what to build*. Today three of those four sections are well-shaped; idealUser is the broken link. Fixing it makes the blueprint read as one continuous story instead of two well-shaped chunks separated by a generic gap.
- **Why sequenced now**: Per Highest-Leverage Move Contract Rule #3 ("integration over isolation"), idealUser sits *between* Capability (just fixed) and Transformation/VersionOne (already fixed) in the user's read order. Continuing the audience-specificity chain serves blueprint-as-artifact integrity. Per Rule #2 ("system-level over surface fixes"), this is another surface-level fix that compounds the architectural decoupling work.
- **Why now vs the other backlog items**: Vocabulary expansion (still v1.0.10 #3) remains marginal-distributed gain. Shared module extraction is now strongly indicated (three inline synthesizers) but should wait one more pass so the extraction captures all three patterns at once.
