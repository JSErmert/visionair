**Bottleneck:**
The system is no longer exploratory. It is live. The next bottleneck is **real user observation data** — none of the governance infrastructure, none of the synthesizer calibration, none of the per-persona harness validation can substitute for observing what an actual first-use session produces from a real person with unstructured potential.

### Highest-Leverage Next Move

**Open the user-testing phase.** Run at least one real first-use session (ideally 3–5) with someone matching the VisionAir core-identity profile — "capable but unclear" people who have real signal but haven't yet translated it into structured progress. Capture: (a) where they hesitated, (b) whether the blueprint felt true to them, (c) whether it surfaced something they didn't already know, (d) whether they would act on it.

### Exact Next Step

No sealed-artifact loop required for user testing itself — that's an observational activity, not a code/governance execution. But:

1. Use the live dev server (or a hosted equivalent) to run real sessions
2. Capture per-session observations in a structured log (can be informal notes)
3. After 3+ sessions: open a governance pass (`v1.1.1` or similar) to analyze patterns, decide calibration adjustments, and seal any resulting code changes per the ARRSC loop
4. Deferred-past-bucket-2 backlog items can be sequenced based on what user testing reveals as most load-bearing

### Why This Move

- The system is built; the question now is whether it does what the doctrine says it does
- User-testing observations are the only input that can falsify the v1.0.9 calibration baseline or confirm v1.0.24's weighting improvements generalize beyond the 10-persona harness
- Deferred polish items (P1 blocker vocabulary, regex conjunction polish, synthesizeReflection extraction) should be sequenced based on what real users actually trip over, not pre-emptively
- The directive's §"One-Line Completion Principle" says v1.1.0 is the moment "a capable but unclear person" gets "a structured, trustworthy path they can actually begin building" — the only way to verify that is to watch one happen

### What Not To Do Yet

1. **Land backlog polish items pre-emptively.** The entire point of v1.1.0 is to gather real observation data before further iteration. Polish decisions should be data-informed.
2. **Re-calibrate synthesis layers based on a single user's reaction.** The 10-persona harness + v1.0.9 calibration baseline remain the stability anchor. User-testing signal is additive, not replacement.
3. **Promote observed patterns to CLAUDE.md via Instruction Assimilation Layer prematurely.** "Recurring" requires multiple independent instances. A single user's confusion is one data point.
4. **Skip governance discipline for v1.1.x passes.** ARRSC still applies. Sealed-artifact + memo-pass + execute loop remains the hard rule for all code/governance changes.
5. **Retrofit prior reports or system-state entries.** Historical record is preserved by design.
