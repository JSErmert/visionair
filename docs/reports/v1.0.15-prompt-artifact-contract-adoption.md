### Gap — no formal gate between decision and execution
The Highest-Leverage Move Contract defines *what* to do next and *why*. It does not define *how the move is expressed and handed off* for execution. Historically the same pass that identified the move also executed it, which made three failure modes possible:
1. **Interpretation drift** between decision and execution
2. **Session-boundary amnesia** if the session ends between decision and execution
3. **Validation fabrication** in reports pre-written with aspirational results (Report Truth Rule violations)

### Tensions resolved at adoption time

Three tensions were flagged before adoption; all three are resolved here:

**(1) Versioning sequencing decision.** Adopted as v1.0.15 following v1.0.4 (SCL) and v1.0.10 (Highest-Leverage Move Contract) precedent — governance adoption consumes a full patch version. `synthesizeIdealUser` moves from v1.0.15 to v1.0.16. Subsequent versions shift by one. The v1.0.13 system-state authority clause is honored via explicit supersession in the new system-state entry.

**(2) Fencing-rule collision.** Memory rule mandates every VisionAir reply is wrapped in a 4-backtick `md` fence. The new contract mandates prompt-generation output is exactly one fenced markdown artifact with no commentary. Both compose: the outer 4-backtick wrapper is the standing chat-reply shape; inside, a single 3-backtick sealed artifact with nothing before or after satisfies the "one fenced artifact" rule at the content level. Documented in the system-state entry §"Fencing-Rule Interaction (resolved)" so future sessions don't re-derive.

**(3) Report Contract interaction.** The Report Contract's Fenced Report Output Requirement applies in report-generation mode; the Prompt Artifact Contract applies in prompt-generation mode. The two modes are mutually exclusive per pass. Invocation patterns ("Create sealed execution artifact for vX.Y.Z" / "Enter prompt-generation mode for vX.Y.Z") are the only triggers for prompt-generation mode; outside those invocations, prior rules govern. Documented in the system-state entry §"Explicit Rules Going Forward" so invocation semantics are persistent.
