### Root cause

The exclusion regex is:
```ts
const exclusionRe = /\b(?:no|without)\s+([a-z][a-z]*(?:[\s-]+[a-z][a-z]+)?)\b/gi
```

The capture group `([a-z][a-z]*(?:[\s-]+[a-z][a-z]+)?)` matches 1 OR 2 words, and JavaScript regex is greedy by default — it prefers the 2-word match when possible.

For input *"no doubt this will work"*:
- Regex matches `"no doubt this"` (full 2-word match at the `this` word)
- Capture group = `"doubt this"` (2 words)
- `term = "doubt this"` after normalization
- Denylist check: `['one', ..., 'doubt', ...].includes('doubt this')` → **false** (the string `"doubt this"` is not in the denylist of single tokens)
- `exclusions.push('doubt this')` → fabricates the false-positive bullet

The denylist only blocks single-token captures. Every real-world discourse marker is followed by at least one other word (the sentence continues), so every real-world discourse marker produces a 2-word capture that slips through the denylist.

**The sealed design filters exactly the cases that don't occur in natural prose.** The 10-persona harness byte-identical result (V4 pass) is consistent with this — no persona uses a bare `"no doubt"` + period, so no persona was affected by the extended denylist in either direction. V4 passed because the extension had zero effect, not because the extension worked.

## Root-Cause Analysis + Proposed Re-Seal Design

### Why both memo-passes missed this
The user-side memo-pass produced T1–T4 focused on validation language, synthetic-test method, parity-check robustness, and token ambiguity. None examined the regex/denylist interaction directly.

My Claude-side memo-pass gave "Pass" and validated T1–T4 individually. I did not trace through the regex greedy-match behavior on a discourse-marker input. The flaw existed in my original sealed artifact's design, was preserved through the re-seal, and only surfaced when V5 was executed as designed.

### Governance-positive framing
This is exactly the scenario V5 synthetic validation exists for. Without that validation step, the denylist extension would have shipped with a silent no-op effect (V4 would pass because no persona triggers it; no one would notice bug_011 was still open until someone wrote "no doubt" in a real session). The v1.0.19 contract's standing rule that synthetic validation MUST accompany denylist-style changes caught this. **The system worked.**

### Proposed re-seal design (for v1.0.21 second re-seal)

The fix: check the **first word** of the capture against the denylist, not the entire capture.

```ts
const exclusions: string[] = []
const exclusionRe = /\b(?:no|without)\s+([a-z][a-z]*(?:[\s-]+[a-z][a-z]+)?)\b/gi
const denylist = new Set([
  'one', 'need', 'longer', 'sense', 'idea', 'matter',
  'doubt', 'way', 'question', 'problem', 'time',
  'rush', 'hurry', 'surprise', 'kidding', 'wonder',
  'worries', 'offense', 'thanks', 'joke', 'chance',
  'clue', 'contest',
])
let m: RegExpExecArray | null
while ((m = exclusionRe.exec(text)) !== null) {
  const term = m[1].toLowerCase().replace(/\s+/g, ' ')
  // v1.0.21: check first word of capture against denylist
  // (regex captures up to 2 words greedily; discourse markers like "no doubt this"
  // produce 2-word captures where "doubt" is the discourse marker)
  const firstWord = term.split(/[\s-]/)[0]
  if (!denylist.has(firstWord)) {
    exclusions.push(term)
  }
}
```

**Edge-case reasoning:**
- `"no doubt this"` → capture `"doubt this"` → firstWord `"doubt"` → denylisted → filtered ✓
- `"no problem"` alone → capture `"problem"` → firstWord `"problem"` → denylisted → filtered ✓
- `"no backend integration"` → capture `"backend integration"` → firstWord `"backend"` → not denylisted → passed ✓
- `"no UI"` → capture `"ui"` → firstWord `"ui"` → not denylisted → passed ✓
- `"no real value"` → capture `"real value"` → firstWord `"real"` → not currently denylisted → passed (status quo; may add `"real"` to denylist in polish if needed)
