## Readiness / Next Move

### Current System State

**Working:**
- Reflection synthesis (v1.0.5/v1.0.6) — robust across emotional, capability-rich, weak, and gibberish input. Calibration score in v1.0.9: highest of any surface.
- Transformation synthesis (v1.0.7) — translates emotional before/after into structural state, propagates correctly into the live transformation card and the blueprint reveal.
- Structural Constraint Layer holds across 100% of personas tested in v1.0.9 — no raw emotional phrasing reaches the artifact.
- Reporting infrastructure: contract live, 8 governed reports written (v1.0.0 → v1.0.9), all conforming to the 9-section structure.
- Runtime: live dev server + ngrok tunnel exposing the full session at `https://unwired-pasquale-conciliatory.ngrok-free.dev/session`.

**Not working / weak:**
- **Core Capability section in the blueprint shows reflection-style meta-commentary**, not capability statements. For 4–5 of 10 personas evaluated in v1.0.9, this section reads as system-talking-about-its-own-input rather than user-talking-about-their-own-capability. Worst case (P8 builder): "What you shared is real but is still in unstructured form…" rendered as Core Capability for a confident two-time founder.
- versionOne falls to generic fallback for 9 of 10 personas. The most concrete blueprint section becomes the most generic.
- Builder vocabulary (shipped, MRR, pilot, churn, scope) and somatic vocabulary (felt sense, regulation, embodiment) are not in any translation table.

**Bottleneck:**
The Core Capability surface is wired to the wrong synthesizer. `synthesizeReflection` is purpose-built for diagnosing seed-prompt input, not for composing capability statements from the user's deliberate answers to capability questions. This is a data-flow misrouting that produces wrong-category output for the most-prominent blueprint section. Fixing it is the single change with the highest blueprint-prominence ratio.

### Highest-Leverage Next Move

**Decouple Core Capability from Reflection synthesis. Replace it with a dedicated `synthesizeCapability` that produces capability statements (what the user can reliably do for someone else) from the joined capability answers.**

### Exact Next Step

In a single new pass:

1. **Modify `app/session/page.tsx`** — replace the line:
   ```ts
   capability: capabilityRaw
     ? synthesizeReflection(capabilityRaw).join(' ')
     : '',
   ```
   with:
   ```ts
   capability: synthesizeCapability(state.capability).join(' ')
   ```

2. **Add `synthesizeCapability(answers: string[])` to a new helper** (either inline in `page.tsx` or in a new module — to be decided per scope).

3. **Implementation shape** — `synthesizeCapability` should:
   - take the array of 5 capability-question answers
   - detect the same themes already in `themePatterns` (structure, clarity, guiding, building, teaching, analysis, problemSolving, translating)
   - additionally detect a small set of capability-statement signals: explicit "I help [X] do [Y]" patterns, "people come to me for [X]", strong action verbs paired with target nouns
   - emit 3–4 bullets in the form: *"You can reliably help [target] [action]."* / *"You consistently produce [outcome] for [user-type]."* — externally observable capability statements, NOT meta-commentary
   - fallback when capability answers are weak should explicitly flag the gap ("Capability has not yet been named in operational terms") rather than fall through to reflection-style framing

4. **Remove the `synthesizeReflection` import in `page.tsx`** if no longer used elsewhere.

5. **Verify by running the v1.0.9 personas through the harness** with the new wiring; expect P2, P8, P9, P10 capability scores to improve without regression on the others.

6. **Write report v1.0.11** documenting the decoupling, with before/after capability bullets for at least P8 and P2.

The pass scope is: **one file edit to `page.tsx` + one helper function**. Estimated 30–60 minutes of work. No UI changes, no other surfaces touched.

### Why This Move

- **Impact relative to alternatives**: Lifts the most-prominent blueprint section out of wrong-category output. v1.0.9 scored Core Capability as wrong-frame for 4–5 of 10 personas — this is roughly half the user base getting the wrong content type for the section they read first.
- **What it unlocks**: Once Capability shows real capability statements, the system stops feeling like "the same reflection text twice" (currently the Reflection screen and the blueprint Capability section share the same synthesizer output). The two surfaces become differentiated, which is what the doctrine intends.
- **Why sequenced now**: The contract's Prioritization Rule #4 — "prefer data flow fixes over logic tweaks" — directly favors this move over recommendation #2 (versionOne action-translator, which requires *new* logic). Capability decoupling is a wiring fix; versionOne is a new translator. Wiring fixes go first.
- **Why now vs later**: Capability is the user's first impression of the artifact. Every subsequent improvement (versionOne, builder vocabulary, idealUser) lands on a foundation where the most prominent section is wrong-shaped. Fix the prominent section first.

### What Not To Do Yet

1. **Build the versionOne action-translator (v1.0.9 recommendation #2)** — Lower leverage than Capability decoupling because (a) it requires designing new logic, not just rewiring, and (b) versionOne sits below Capability in the blueprint visual hierarchy. Do this *immediately after* Capability decoupling lands and is verified, then re-run the persona harness to see if versionOne becomes the new biggest gap.

2. **Expand translation tables for builder/somatic vocabulary (v1.0.9 recommendation #3)** — Lower leverage because vocabulary expansion is a continuous, never-finished task; doing it in isolation produces marginal scores improvements without addressing the structural data-flow misrouting. Do this iteratively *after* both top fixes land, prioritizing whichever vocabulary gap real users actually surface.

3. **Register the three contracts in `.claude/CLAUDE.md`'s Active Governing References list** — Lower leverage because contracts already self-enforce via their authority language; the CLAUDE.md registration is documentation for discoverability, not a runtime change. Per the new contract's own Prioritization Rule #5 ("prefer runtime behavior alignment over documentation updates"), defer until after a runtime pass completes that benefits from explicit cross-reference.

4. **Extract synthesis helpers into a shared module** (open since v1.0.5, expanded by v1.0.7, restated in v1.0.9) — Lower leverage right now because the next two recommended fixes (Capability, versionOne) involve adding new functions and modifying existing wiring. Wait until the new functions stabilize, then extract in one consolidating pass to avoid re-extracting twice. Do this *after* both Capability decoupling and versionOne action-translator are in place.
