# Blueprint Synthesis Integration

## Report Version
v1.0.8

## Purpose
Make the Structured Opportunity Blueprint draw from synthesized outputs as its source of truth instead of raw user input. Wire the existing reflection and transformation synthesizers (built in v1.0.5/v1.0.6/v1.0.7) into the blueprint composition step in `page.tsx` so the final artifact never contains raw emotional phrasing.

## Trigger
User prompt **"Run a Blueprint Synthesis Integration pass"** on 2026-04-21. Constraints: only change data flow and source-of-truth; do not change UI/layout; do not modify synthesis logic.

## State Observed (pre-execution)
`app/session/page.tsx` composed `blueprintData` like this:

```ts
const blueprintData = {
  capability: formatCapability(state.capability),       // raw join with spaces
  problemSpace: formatProblemSpace(state.problemSpace), // already structured
  idealUser: state.idealUser,                            // RAW textarea echo
  transformation: formatTransformation(...),             // synthesized in v1.0.7
  opportunityForm: formatOpportunityForm(...),           // already structured
  versionOne: state.versionOne,                          // RAW textarea echo
  pathForward: state.pathForward,                        // RAW textarea object
}
```

Three fields (`capability`, `idealUser`, `versionOne`) and the three pathForward sub-fields fed user-typed text directly into the blueprint. Any emotional phrasing the user typed (e.g., "lost", "worthless", "safe space", "I feel overwhelmed") would round-trip into the final artifact unchanged, violating the Structural Constraint Layer.

`synthesizeReflection` existed in `app/session/flow/reflection.tsx` but was unexported, so it could not be used outside that file.

## Action Taken
Two files modified — both as data-flow changes only. No synthesis logic was changed; the only modification to `reflection.tsx` was adding the `export` keyword to expose the existing function.

### `app/session/flow/reflection.tsx` — single-keyword change
```diff
-function synthesizeReflection(seedInput: string): string[] {
+export function synthesizeReflection(seedInput: string): string[] {
```
No body change. No parameter change. The function's behavior is identical.

### `app/session/page.tsx` — data-flow rewire
- Updated `Reflection` import to also pull `synthesizeReflection` as a named import (alongside the existing `Reflection` default).
- Rewrote the `blueprintData` composition to route raw fields through synthesizers:

```ts
const capabilityRaw = formatCapability(state.capability)
const blueprintData = {
  capability: capabilityRaw
    ? synthesizeReflection(capabilityRaw).join(' ')
    : '',
  problemSpace: formatProblemSpace(state.problemSpace),
  idealUser: state.idealUser.trim()
    ? structuralizeBefore(state.idealUser).join(' ')
    : '',
  transformation: formatTransformation(
    state.transformationBefore,
    state.transformationAfter
  ),
  opportunityForm: formatOpportunityForm(state.opportunityForm),
  versionOne: state.versionOne.trim()
    ? structuralizeAfter(state.versionOne).join(' ')
    : '',
  pathForward: state.pathForward,
}
```

### Per-field source-of-truth decisions

| Section | Pre-pass source | Post-pass source | Rationale |
|---|---|---|---|
| Core Capability | `formatCapability(state.capability)` (raw join) | `synthesizeReflection(joined capability answers).join(' ')` | The reflection synthesizer is purpose-built for capability/value-pattern detection — same machinery the user already saw on the Reflection screen, applied to the joined capability answers |
| Aligned Problem Space | `formatProblemSpace(state.problemSpace)` | unchanged | Already structured (radio → fixed phrase) |
| Ideal User | `state.idealUser` (raw) | `structuralizeBefore(state.idealUser).join(' ')` | Ideal-user text typically describes the user's struggle/state, which is exactly what `structuralizeBefore` is calibrated for |
| Transformation Promise | `formatTransformation(...)` (already synthesized in v1.0.7) | unchanged | Already routes through `structuralizeBefore`+`structuralizeAfter` |
| Opportunity Form | `formatOpportunityForm(state.opportunityForm)` | unchanged | Already structured (radio → fixed phrase) |
| First Buildable Version | `state.versionOne` (raw) | `structuralizeAfter(state.versionOne).join(' ')` | Version-one text describes the resolved/realized state of the system — aligned with `structuralizeAfter`'s vocabulary |
| Guided Path Forward | `state.pathForward` (raw object) | unchanged (deliberate) | Action-oriented content (e.g. "test with 3 users this week"). Running through state translators would replace specific actions with generic state fallbacks, destroying the value of the bucketed list. The immediate/near-term/later bucketing is itself the structural shape. Documented as open follow-up below. |

### Out-of-scope explicitly preserved
- No synthesis function logic changed (only the `export` keyword added)
- No UI or layout change
- Blueprint card (`blueprint.tsx`) untouched — the `BlueprintData` type is unchanged, so `SectionCard` continues to render strings as before
- Other flow screens (`welcome`, `starting-point`, `seed-prompt`, `reflection`, `capability`, `problem-space`, `ideal-user`, `transformation`, `opportunity-form`, `version-one`, `path-forward`, `closing`) untouched
- Doctrine, contracts, governance: untouched
- `console.log("SYNTHESIS RUNNING", ...)` from the verification pass remains in `synthesizeReflection` and now also fires when blueprint composition runs (an honest, useful side-effect for verification — still on the open follow-up list to remove later)

## Result
- Blueprint sections that used to echo raw user phrasing now show structurally translated content
- The transformation card (live UI) and the blueprint card (final artifact) now show *the same* structurally-translated transformation
- The capability section of the blueprint is now a real reflection synthesis over the user's capability answers — not just a space-joined dump
- The pathForward section is the only remaining surface where raw text reaches the artifact, deliberately preserved because action content does not benefit from state translation

## Readiness / Next Move
**Readiness**: The Structured Opportunity Blueprint now uses synthesized outputs as its source of truth for 6 of 7 sections. The blueprint matches what users see on the live Reflection and Transformation screens, in the same structured, translated register. Raw emotional phrasing cannot reach those 6 sections. Reflection-screen output and blueprint Capability section now share the same synthesizer, so they look like the same system speaking — not two different surfaces.

**Highest-leverage next move**: **Path Forward synthesis decision** — pick one of:
1. **Leave as-is** and rely on the bucketed structure (immediate/near-term/later) as sufficient framing. Keeps user-typed actions specific.
2. **Add a path-forward-specific filter** that catches emotional phrases inline while preserving action verbs. Requires new synthesis logic, which is out of scope for this pass but is the right move if the user wants strict "no raw phrasing anywhere."
3. **Apply `structuralizeAfter`** uniformly. Closes the leak but destroys specific actions on inputs without translatable matches. Not recommended.

Recommendation: option 1 for now (bucketing IS structure), revisit if real users surface emotional phrasing in their next-step text.

**Other strong next-move candidates** (carried from prior reports):
