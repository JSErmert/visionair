# Core Capability Decoupling

## Report Version
v1.0.11

## Purpose
Execute the v1.0.10 highest-leverage move: decouple the Core Capability blueprint section from `synthesizeReflection`. Replace the misrouted reflection-synthesis call with a dedicated `synthesizeCapability` that produces capability statements (what the user can reliably do for someone else) rather than reflection-style meta-commentary about the user's input shape.

## Trigger
User prompt **"VisionAir Core Capability Decoupling Pass"** on 2026-04-21, executing the singular next move identified in v1.0.10 under the Highest-Leverage Move Contract.

## State Observed (pre-execution)
`app/session/page.tsx` constructed the blueprint's Core Capability field by routing the joined capability answers through `synthesizeReflection`:

```ts
const capabilityRaw = formatCapability(state.capability)
const blueprintData = {
  capability: capabilityRaw
    ? synthesizeReflection(capabilityRaw).join(' ')
    : '',
  // ...
}
```

Because `synthesizeReflection` is purpose-built for diagnosing seed-prompt input (emotional-dominant branch, fallback structuralization, weak-signal detection), routing capability answers through it produced wrong-category output for 4–5 of the 10 personas evaluated in v1.0.9. Worst-case outputs:

- **P8 builder**: *"What you shared is real but is still in unstructured form — there is signal here that has not yet been separated into a capability, a problem, or a direction…"* — system declared a confident two-time founder's capability "unstructured" despite rich content
- **P2 emotional**: *"The language you used points at something structural: the situation lacks direction and structure…"* — reflection-style framing where capability statements should be
- **P9 wellness**: identical emotional-dominant template as P2 — vocabulary erasure
- **P10 mixed**: same emotional-dominant template

## Action Taken
Modified only `app/session/page.tsx`. No other file touched. Three sequential edits:

### Edit 1 — Add `synthesizeCapability` helper inline
Added below `formatCapability`, before `formatProblemSpace`. Consists of:
- `CapabilityTheme` type (8 themes, same labels as reflection's themes for consistency)
- `capabilityThemePatterns` regex map — *expanded* over reflection's table to include capability-relevant vocabulary missing from reflection's tables: `scope`, `plan`, `ship`, `product`, `prototyp`, `launch`, `MRR`, `SaaS`, `v1` (builder vocabulary); `hold space`, `presence`, `retreat`, `session`, `workshop`, `facilitat` (wellness/coaching vocabulary); `bottleneck`, `dysfunctional`, `broken`, `diagnos`, `trac` (problem-solving vocabulary)
- `capabilityTargetNouns` — 20 target-audience patterns mapping to canonical labels (engineers, founders, students, small business owners, designers, consultants, coaches, teams, women, nontechnical builders, overwhelmed people, stuck people, people who feel lost, scattered or fragmented people, burned-out or anxious people, disconnected people, etc.)
- `capabilityActionByTheme`, `capabilityStrengthByTheme`, `capabilityValueByTheme` — three template tables, one bullet template per theme, each *capability-shaped* (e.g., *"You can reliably help [target] [action]"*) rather than reflection-shaped
- `detectCapabilityThemes(text)`, `detectCapabilityTargets(text)` — regex-scoring detectors
- `synthesizeCapability(answers: string[])` — composes 3–4 bullets:
  - **Bullet 1** (capability statement): `"You can reliably help [target] [action]"` from top theme + first target. Falls back to `"You can reliably produce real value…"` capability framing when no theme matches.
  - **Bullet 2** (strength): from second theme; falls back to target-pairing or top-theme strength.
  - **Bullet 3** (value): from top theme value template.
  - **Bullet 4** (only when content is rich — 3+ themes or 2+ targets): pattern-recognition statement using secondary target.
- Empty-input branch returns capability-shaped fallback explicitly flagging the operational naming gap, NOT reflection-style framing.

### Edit 2 — Remove `synthesizeReflection` import
```diff
-import Reflection, { synthesizeReflection } from './flow/reflection'
+import Reflection from './flow/reflection'
```
`synthesizeReflection` is no longer used in `page.tsx`; the Reflection screen still imports it internally for its own use.

### Edit 3 — Rewire blueprint capability source
```diff

-    ? synthesizeReflection(capabilityRaw).join(' ')

```
`formatCapability` is no longer called for the blueprint pipeline (it was only ever a `.join(' ')` helper for the deprecated wiring); kept in place because removing it is out of scope for this pass.

### Out-of-scope explicitly preserved
- `app/session/flow/reflection.tsx` — untouched (synthesizeReflection still serves the Reflection screen)
- `app/session/flow/transformation.tsx` — untouched (structuralizeBefore/After still serve their surfaces)
- All other flow screens — untouched
- `app/session/flow/blueprint.tsx` — untouched (UI/layout)
- All contracts, doctrine, governance — untouched
- Test harness at `C:/Users/JSEer/AppData/Local/Temp/visionair-eval.mjs` — updated to mirror the new function for re-validation; lives outside the repo

## Result
- `app/session/page.tsx` now contains an inline, capability-shaped synthesizer
- The blueprint Core Capability section produces capability statements about what the user can reliably do for someone else
- The Reflection screen output and the blueprint Core Capability section now use *different* synthesizers — the two surfaces are no longer collapsed into the same text

## Validation

### P8 — Highly actionable builder (the worst v1.0.9 case)

**Before (v1.0.9):**
> *"What you shared is real but is still in unstructured form — there is signal here that has not yet been separated into a capability, a problem, or a direction. The functional gap is that the input has not yet been named in terms of what someone else would receive or experience as a result. This is a normal early-stage state, not a deficit — the input is in a layer that needs structural separation, not more reflection. What matters now is restating the input in terms of what someone else would receive — that single shift gives the system a structural anchor to work from."*

**After (v1.0.11):**
> *"You can reliably help founders turn ideas and signals into something real, shaped, and externally observable. Your strength is in turning scattered material into structure others can follow. The value you create is something real, shipped, and observable where there was previously only possibility."*

The "founders" target was caught (P8's capability answers contain "founders" multiple times). The building theme dominated (matches: "shipped", "products", "MRR", "ship", "v1", "build"). The structure theme came second (matches: "scope", "scope creep"). Output now correctly describes a confident two-time founder's capability. **Validation case 1 passes.**

### Why This Move

- **Impact relative to alternatives**: With Capability fixed, versionOne is now the single most visible quality drop in the blueprint. 9 of 10 personas get the same generic fallback paragraph. Fixing it would lift Opportunity Relevance and Self-Understanding Gain scores across nearly the entire persona space.
- **What it unlocks**: Once versionOne synthesizes the user's actual scope decision, the blueprint becomes a buildable artifact for the first time — the user can read Core Capability + First Buildable Version together and see a coherent "this person can do X for Y, and the smallest version of that is Z." Currently those two sections feel disconnected because Z is generic fallback.
- **Why sequenced now**: Per the Highest-Leverage Move Contract Rule #3 ("prefer integration over isolation"), the next surface should be the one most coupled to the just-fixed surface. Capability and versionOne are the two surfaces the user reads consecutively in the blueprint and that together describe "what you can do" + "what to build." Sequence integrity argues for versionOne immediately after Capability. Per Rule #2 ("system-level over surface fixes"), this is the next surface-level fix that compounds the prior architecture-level fix rather than diluting attention to vocabulary expansion.
- **Why now vs the other backlog items**: Vocabulary expansion (#3 in v1.0.10's ranking) is continuous and marginal; doing it before versionOne would marginally improve scores everywhere without fixing the most visible single drop. Shared module extraction is premature until versionOne stabilizes.

### What Not To Do Yet

1. **Expand reflection/transformation translation tables for builder + somatic vocabulary (v1.0.10 carryover)** — Lower leverage than versionOne fix because vocabulary improvements distribute marginal gains across many small surfaces while versionOne is a single critical surface failing 90% of the time. Do this iteratively *after* versionOne lands and the harness reveals which vocabulary gaps now matter most.

2. **Tune the v1.0.11 capability strength bullet (bullet 2)** to avoid weakly-matched secondary themes (P2, P9 got "building" inappropriately) — Lower leverage because the strength bullet is still capability-shaped and below the threshold of "wrong category." Defer to a refinement pass once at least 2 more synthesis surfaces are upgraded and the strength-bullet pattern can be addressed across all of them at once.

3. **Extract synthesis helpers into a shared module** (open since v1.0.5) — Lower leverage right now because the inline `synthesizeCapability` plus the upcoming inline `synthesizeVersionOne` are still in flux. Wait until both stabilize, then extract in one consolidating pass; same reasoning given in v1.0.10.

4. **Register the three contracts in `.claude/CLAUDE.md`** — Same reasoning as v1.0.10: documentation cleanup, not runtime alignment. Per Highest-Leverage Move Contract Rule #5, defer until a runtime pass benefits from explicit cross-reference.
