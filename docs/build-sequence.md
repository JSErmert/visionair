# VisionAir Build Sequence  
  
## Purpose  
This document defines the strict build order for VisionAir after re-founding.  
  
It exists to prevent:  
- drift  
- premature expansion  
- feature sprawl  
- rebuilding from old assumptions  
- confusing ambition with progress  
  
This is a development-governance document.  
  
Its job is to answer:  
  
> What gets built first, what gets built later, and what must not be built before the soul of VisionAir is proven?  
  
---  
  
## Core rule  
VisionAir must not be built as a broad platform first.  
  
It must first prove one sacred experience:  
  
> a capable but unclear person enters in fog and leaves with structured, trustworthy movement.  
  
If that experience is not real, nothing else matters yet.  
  
---  
  
## First-principles build order  
  
### Phase 0 — Re-founding alignment  
Before building anything, the following documents must exist and be treated as source-of-truth references:  
  
1. VisionAir Founding Doctrine and First Experience Charter  
2. VisionAir Preserve / Reframe / Release Audit  
3. VisionAir PRD  
4. VisionAir first-session wireframe / flow spec  
  
### Exit condition for Phase 0  
The product can be described in one clear sentence:  
  
> VisionAir is a human-centered governed intelligence environment that helps capable but unclear people turn what they already carry into something structured, trustworthy, and real.  
  
If the team cannot hold that line clearly, do not build yet.  
  
---  
  
## Phase 1 — Prove the first sacred experience  
### Build only:  
The **Structured Opportunity Session**  
  
This is the first and only sacred experience that must be proven before broader expansion.  
  
### Goal  
Take the user from:  
  
**"I know there’s something here, but I can’t structure it."**  
  
to:  
  
**"I can clearly see what I have, who it helps, what it should become, and what my first real move is."**  
  
### Required outputs  
The session must produce a **Structured Opportunity Blueprint** with these 7 sections:  
  
1. Core Capability  
2. Aligned Problem Space  
3. Ideal User  
4. Transformation Promise  
5. Opportunity Form  
6. First Buildable Version  
7. Guided Path Forward  
  
### What must be built in Phase 1  
- welcome / permission screen  
- starting-point selection  
- seed signal capture  
- reflection back  
- capability clarification  
- problem-space alignment  
- ideal-user definition  
- transformation definition  
- opportunity-form recommendation  
- first-buildable-version grounding  
- blueprint reveal  
- guided next steps  
  
### What matters most in Phase 1  
- clarity  
- trust  
- emotional coherence  
- guided progression  
- strong synthesis  
- real movement  
  
### Exit condition for Phase 1  
A user can go through the session and honestly say:  
  
- I feel clearer  
- this fits me  
- I can see what I actually have  
- I know what to do next  
  
If this is not happening, do not move to Phase 2.  
  
---  
  
## Phase 2 — Strengthen the sacred experience  
Once the first experience works, improve its depth and reliability before expanding outward.  
  
### Build next:  
- better synthesis quality  
- better reflection language  
- stronger refinement loops  
- clearer blueprint formatting  
- more believable and useful guided path forward  
- calmer and more elegant UX  
- improved continuity between steps  
- stronger truth-preserving follow-up questions  
  
### Focus of Phase 2  
Not more features.  
  
Better:  
- signal interpretation  
- trust  
- personalization  
- coherence  
- authored-feeling output  
- real reduction of fog  
  
### Exit condition for Phase 2  
The first session consistently feels:  
- trustworthy  
- non-generic  
- emotionally meaningful  
- clearer than doing it alone  
- worth returning to  
  
Only then should VisionAir expand.  
  
---  
  
## Phase 3 — Add deepening loops  
After the first sacred experience is strong, add **structured refinement**, not platform sprawl.  
  
### Build next:  
- refine one blueprint section at a time  
- deepen capability definition  
- sharpen user definition  
- test alternate problem spaces  
- compare opportunity forms  
- revise version-one scope  
- regenerate guided next steps with more precision  
  
### Purpose  
Allow the user to deepen and refine what emerged in the first session.  
  
### Important rule  
These loops must deepen the first truth, not restart the user in chaos.  
  
### Exit condition for Phase 3  
A user can return to VisionAir and make their blueprint:  
- more precise  
- more aligned  
- more buildable  
without feeling lost or reset.  
  
---  
  
## Phase 4 — Version-one planning environment  
Only after VisionAir clearly helps users discover aligned opportunity should it begin helping them shape execution.  
  
### Build next:  
- version-one planning workspace  
- scope boundary tools  
- first validation checklist  
- first user-test planning  
- offer / product-shape planning  
- simple roadmap assistance  
- what-to-build-now / what-to-wait-on logic  
  
### Purpose  
Move from structured opportunity into structured first execution.  
  
### Important rule  
VisionAir should not become a generic project manager.  
It should remain a guided progression system.  
  
### Exit condition for Phase 4  
The user can move from:  
- “I know what this is”  
to:  
- “I know what version one is and how to begin testing it.”  
  
---  
  
## Phase 5 — Branching and comparative paths  
Only after opportunity + version-one planning are strong should VisionAir begin supporting branching.  
  
### Build next:  
- compare two opportunity paths  
- compare two user directions  
- compare two forms  
- branch and reconverge logic  
- confidence / fit comparison  
- preserve continuity across branches  
  
### Purpose  
Help users explore possibility without losing structure.  
  
### Important rule  
Branching must serve clarity, not option overload.  
  
### Exit condition for Phase 5  
Branching helps users feel:  
- more certain  
not:  
- more scattered  
  
---  
  
## Phase 6 — Persistent workspace  
Only after the journey is real should a more persistent product environment emerge.  
  
### Build next:  
- saved blueprint history  
- progress memory  
- structured return sessions  
- continuity across decisions  
- evolving project state  
- session-to-session orchestration memory  
  
### Purpose  
Turn VisionAir from a single sacred experience into an evolving governed environment.  
  
### Important rule  
Persistence should preserve continuity, not create admin burden.  
  
---  
  
## Explicitly forbidden before the sacred experience is proven  
  
The following must **not** be built before Phase 1 and Phase 2 are clearly working:  
  
### Forbidden category 1 — Platform sprawl  
Do not build:  
- many user personas  
- broad multi-product ecosystems  
- communities  
- marketplaces  
- complex dashboards  
- massive role systems  
  
### Forbidden category 2 — Startup-tool drift  
Do not build:  
- hustle dashboards  
- founder gamification  
- generic startup coaching flows  
- “launch fast” productivity language  
- noisy KPI-first interfaces  
  
### Forbidden category 3 — Premature automation  
Do not build:  
- complex auto-generation trees  
- advanced branching systems  
- multi-agent orchestration layers  
- automation for steps that have not yet been emotionally and structurally proven  
  
### Forbidden category 4 — Decorative complexity  
Do not build:  
- visual flourishes with no grounding function  
- elaborate interactions that do not reduce fog  
- aesthetic systems that distract from clarity  
- symbolic elements that do not support progression  
  
### Forbidden category 5 — Generic business-plan logic  
Do not build:  
- late-stage business planning modules  
- financial forecasting layers  
- advanced startup documents  
- investor-oriented systems  
unless the first sacred experience already proves clear opportunity and user fit  
  
---  
  
## Build priority stack  
  
### Priority 1  
**Can the user feel seen clearly enough to move?**  
  
### Priority 2  
**Can the product turn vague internal truth into structured external form?**  
  
### Priority 3  
**Can the user trust the output enough to act on it?**  
  
### Priority 4  
**Can the product preserve clarity across refinement?**  
  
### Priority 5  
**Can future layers deepen progression without diluting the soul?**  
  
If a feature does not strengthen one of these priorities, it should not be built yet.  
  
---  
  
## Build sequence in compact form  
  
### Build first  
- first sacred experience  
- structured opportunity blueprint  
- reflection quality  
- synthesis quality  
- next-step quality  
  
### Build second  
- refinement loops  
- stronger continuity  
- improved output quality  
- stronger problem/user/form precision  
  
### Build third  
- version-one planning  
- validation guidance  
- execution-path shaping  
  
### Build fourth  
- branching and comparative paths  
- continuity memory  
- persistent workspace  
  
### Build much later  
- broad platform layers  
- ecosystem expansion  
- advanced automation  
- multi-user or community systems  
- anything that turns VisionAir into generic software  
  
---  
  
## Development decision filter  
Before building anything new, ask:  
  
### 1. Does this strengthen the first sacred experience?  
If no, do not build it yet.  
  
### 2. Does this reduce fog or increase agency?  
If no, do not build it yet.  
  
### 3. Does this preserve VisionAir’s identity as a governed progression environment?  
If no, do not build it yet.  
  
### 4. Would this still belong if VisionAir were being invented for the first time today?  
If no, do not build it yet.  
  
### 5. Is this a depth move or a distraction move?  
If it is distraction, cut it.  
  
---  
  
## Founder directive  
VisionAir must be built in the order of truth, not the order of excitement.  
  
That means:  
  
- prove the soul first  
- deepen the soul second  
- expand only after proof  
- never let future ambition bury the sacred experience  
  
---  
  
## One-line build compass  
**Build only what helps the user move from fog to structured agency.**
