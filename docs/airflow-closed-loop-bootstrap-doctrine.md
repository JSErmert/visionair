# AirFlow Closed-Loop Bootstrap Doctrine

## Purpose
This document teaches the full AirFlow bootstrap pattern end-to-end.

It defines how a system moves from:
- truth
- to structure
- to governance
- to scaffold
- to injection
- to evaluation
- to the next highest-leverage move

This is the doctrine for closed-loop bootstrap orchestration.

It exists so future chats, future repos, and future Claude Code sessions can inherit the same high-leverage sequencing method instead of rebuilding it from scratch.

---

## Core Definition
AirFlow is a recursive, constraint-driven, first-principles orchestration method that repeatedly identifies and executes the highest-leverage next action.

Its purpose is not just to plan work.

Its purpose is to:
- create the right order of truth
- prevent drift
- minimize wasted effort
- preserve system identity
- make the next best move visible after each completed move

---

## Closed-Loop Definition
AirFlow becomes a closed loop when it can do all of the following:

1. define what is true
2. define what exists
3. define what is allowed
4. define what must not happen yet
5. seed a system into reality
6. inspect the resulting state
7. identify the new highest-leverage next move
8. repeat

A bootstrap is not closed-loop if it only seeds files.

A bootstrap becomes closed-loop when the system can evaluate the newly created state and govern its own next move.

---

## Core Principle
Build in the order of truth, not the order of excitement.

That means:
- define essence before features
- define structure before scale
- define constraints before growth
- define governance before expansion
- define scaffold before abstraction
- define the next move only after the current move becomes real

---

## AirFlow Method Stack

### 1. First-Principles Decomposition
Reduce the system to its irreducible truths.

Ask:
- what is this really for?
- who is it really for?
- what transformation must it create?
- what is the first thing that must become real?

### 2. Constraint-Driven Design
Define what is:
- in scope
- out of scope
- forbidden early
- allowed later only under conditions

Constraints are not restrictions on creativity.
They are protections for leverage.

### 3. Iterative Leverage Sequencing
At each stage, ask:

> What is the highest-leverage next move from the current state?

Not:
- what is the biggest thing?
- what is the most exciting thing?
- what is the most advanced thing?

Only:
- what unlocks the most clarity, structure, progress, or correctness next?

### 4. Progressive Formalization
Move from:
- intuition
- to language
- to doctrine
- to structure
- to execution
- to reusable system

This turns fragile insight into durable operational form.

### 5. Recursive Evaluation
After each move, re-evaluate:
- what became clearer?
- what became more real?
- what is now missing?
- what is now the highest-leverage next move?

That evaluation is what closes the loop.

## The AirFlow Closed-Loop Bootstrap Cycle

### Stage 1 — Truth
Define:
- identity
- user
- transformation
- first sacred experience
- core output
- core non-negotiables

### Stage 2 — Doctrine
Capture truth in durable documents.

Examples:
- founding doctrine
- first experience charter
- PRD
- preserve / reframe / release audit
- build sequence
- Phase 1 spec
- Phase 1 checklist

### Stage 3 — Structure
Define the repo skeleton.

Examples:
- repo tree
- folder roles
- authority hierarchy
- growth boundaries

### Stage 4 — Growth Governance
Define:
- what branches exist now
- what branches may exist later
- when each future branch is allowed
- what should never be created early

### Stage 5 — Execution Governance
Create the active orchestration layer for Claude.

Examples:
- CLAUDE.md
- repo rules
- priorities
- workflow loop
- growth constraints

### Stage 6 — Scaffold
Create the smallest truthful code scaffold that can hold the sacred experience.

Examples:
- layout
- global styles
- flow controller
- essential screens
- essential primitives

### Stage 7 — Bootstrap Injection
Transfer the scaffold into the repo through structured batch provisioning.

Examples:
- repository bootstrap manifest
- file-delimited payload
- explicit path + contents transfer

### Stage 8 — State Inspection
Inspect the resulting repo state.

Ask:
- what is now present?
- what is now stable?
- what is now duplicated?
- what is still missing?
- what is too early?

### Stage 9 — Next Highest-Leverage Move
Only after the new state is real, define the next move.

Examples:
- extract repeated primitives
- improve flow controller
- strengthen synthesis quality
- refine artifact output
- create testing docs
- create prompt systems later

### Stage 10 — Repeat
Run the cycle again from the new state.

This is what makes AirFlow recursive, adaptive, and closed-loop.

---

## AirFlow Operating Questions
At every stage, AirFlow should ask:

### Truth questions
- What is this system really trying to do?
- What must remain true no matter what?

### Scope questions
- What belongs now?
- What must wait?

### Leverage questions
- What creates the most clarity or progress next?
- What prevents downstream confusion?

### Constraint questions
- What would be exciting but premature?
- What would create drift if introduced now?

### Structural questions
- Does the current repo state make the system easier to build?
- Is new structure solving a real problem?

### Loop questions
- What changed after the last move?
- What is now the next best move?

---

## What AirFlow Is Not
AirFlow is not:
- random brainstorming
- feature piling
- startup-speed theater
- abstraction for its own sake
- building ahead of proof
- treating every good idea as current scope
- confusing architecture density with system maturity

If a process does these things, it is not AirFlow.

---

## AirFlow Build Ethics

### 1. Truth before elegance
A beautifully worded wrong system is still wrong.

### 2. Structure before ambition
Do not expand a system whose center is still unclear.

### 3. Proof before scale
A sacred experience must become real before the larger platform earns expansion.

### 4. Governance before automation
Do not automate what has not yet been properly governed.

### 5. Recursion before rigidity
The system must be allowed to learn from its own new state.

## AirFlow File Pattern
AirFlow typically produces its systems in this order:

1. doctrine files
2. scope files
3. growth files
4. Claude governance files
5. scaffold files
6. bootstrap manifest
7. evaluation artifacts
8. next-step doctrine

This order may vary slightly, but the principle remains:
**truth -> structure -> governance -> scaffold -> injection -> evaluation -> next move**

---

## AirFlow Bootstrap Manifest Role
The bootstrap manifest is the transfer artifact that moves a defined scaffold into the repo.

It is not doctrine.
It is not design.
It is not long-term governance.

It is:
- a structured injection payload
- explicit file paths
- explicit contents
- explicit order
- minimal ambiguity

This is how AirFlow turns planning into repo state.

---

## AirFlow Closed-Loop Completion Test
A bootstrap process is fully closed-loop only if it can answer all of these:

1. What truth governs the system?
2. What structure currently exists?
3. What growth is allowed next?
4. What rules govern the builder?
5. What scaffold has entered the repo?
6. What is the current resulting state?
7. What is now the highest-leverage next move?
8. What does the system do next because of that state?

If these can all be answered clearly, the loop is closed.

## AirFlow VisionAir Example
In VisionAir, the closed-loop bootstrap pattern looked like this:

1. define VisionAir truth
2. define the first user
3. define the first sacred experience
4. define the first output
5. define doctrine docs
6. define repo structure
7. define repo growth map
8. define Claude governance pack
9. define app scaffold
10. define component primitives
11. inject scaffold through bootstrap manifest
12. inspect repo state
13. choose the next highest-leverage move

That is a real AirFlow cycle.

---

## AirFlow Promotion Rule
Nothing should move upward in authority automatically.

### Prototype -> canonical
Only after proof.

### Archive -> active
Only after review.

### Idea -> branch
Only after structural need.

### Abstraction -> standard
Only after repeated reality.

This keeps AirFlow grounded.

---

## AirFlow Closed-Loop Outputs
A healthy AirFlow loop produces:
- durable doctrine
- minimal clean structure
- explicit governance
- small truthful scaffold
- structured bootstrap injection
- clear evaluation state
- visible next move

If the process produces noise, AirFlow has been broken.

---

## AirFlow Final Law
Do not ask:
- what can be built?

Ask:
- what is the highest-leverage next move that should be built now, given the current truth and current state?

Then build that.
Then evaluate again.
Then repeat.

That is AirFlow.

---

## Short Doctrine Version
AirFlow is a closed-loop orchestration method that repeatedly turns truth into structure, structure into governed execution, execution into real system state, and real system state into the next highest-leverage move.

## One-Line Operating Compass
**Define the truth, build the next highest-leverage move, inspect the new state, and repeat.**
